# LOTTEON-UPDATE-CONTRACT-01 — 롯데ON 기존 상품 수정 계약 조사

> CPO 지시(`COMMERCE-LIFECYCLE-FINAL-03` P1, 2026-09-30).
> **PUT 실행 권한은 이 조사에 포함되지 않는다.** 여기서 하는 것은 「PUT 없이 확인
> 가능한 것을 전부 확인하고, 최소 변경 전략을 설계하는 것」까지다.

---

## 0. 결론 먼저

🔴 **롯데ON 수정은 쿠팡처럼 「하나의 전체 교체 PUT」이 아니다. 축마다 API 가 갈라져
있고, 그중 하나는 «아예 수정할 수 없다».** 그래서 쿠팡에서 쓴 「GET baseline →
통째로 되보내기」를 그대로 옮길 수 없다.

```
쿠팡     PUT seller-products 하나 = 전체 교체        GET 이 곧 baseline
롯데ON   90 상품정보 · 91 가격 · 86 재고 · 92/111 상태   축마다 다른 API
         옵션값·옵션명                                 🔴 수정 «불가»
```

`CLAUDE.md` 의 「두 구조를 억지로 하나로 만들지 않는다」가 그대로 적용된다.

한정하고 있다.

## 1-B. 🟢 2026-09-30 추가 — 공개 자료에서 «봉투 모양» 이 나왔다

이전 조사는 API 센터 페이지를 `WebFetch` 로 열었다가 JS 셸(“NO CONTRACT CONTENT”)에
막혀 여기서 멈췄다. 이번에는 **검색 인덱스에 남아 있는 같은 페이지의 본문**에서
아래를 얻었다(페이지 직접 fetch 는 여전히 JS 셸이다).

```
요청 봉투    spdLst[]            ← 🔴 87 등록과 «같은» 최상위 배열 이름
필수 필드    spdNo (String, 30)  ← 판매자상품번호. 예시 "LO13xxxx"
응답 봉투    returnCode · message · data[]{ epdNo, spdNo, resultCode, resultMessage }
             ← 🔴 87 등록 응답과 «같은» 모양
대상         이름이 「승인 상품 수정」 — 우리 상품 2건은 fnlAprvYn="Y" 로 조건 충족
```

**해석**: 요청/응답 봉투가 87 과 같다는 것은 90 이 **「상품 전문을 통째로 보내고
spdNo 로 대상을 지목하는」 모양** 일 개연성을 높인다. 🔴 개연성은 근거가 아니다 —
아래 미지수 ②는 그대로 남는다.

## 1-C. 🟢 그래서 §4 보수적 전략의 «실패 양식» 이 계산된다

이것이 이번 조사에서 가장 쓸모 있는 결론이다.

94 가 현재 상태 90필드를 «전부» 주므로, §4 는 **아무 칸도 생략하지 않는다.**
그러면 미지수 ②(생략 필드가 지워지는가)가 **적용될 자리 자체가 없다.**

남는 실패 양식은 반대쪽 하나다:

```
94 가 주는데 90 이 받지 «않는» 칸(파생·읽기전용)이 섞여 들어간다
  → 롯데ON 이 그 요청을 «거절» 한다(resultCode 오류)
  → 🟢 거절은 데이터를 바꾸지 않는다. 상품은 그대로다
```

🔴 **즉 보수적 전략의 최악은 「거절」이지 「데이터 손실」이 아니다.** 그리고 성공
했는데 롯데ON 이 일부 칸을 정규화·무시한 경우는 ⑤의 90필드 전수 대조가 잡는다.

이것이 PUT 위험도를 실질적으로 낮추는 근거다 — 다만 **위험이 0 이라는 말은 아니다**
(§6 참조).

## 2. 여전히 «기록이 없는» 것 — 90 의 미지수 셋

`docs/commerce-3b-ux-boundary.md:156` 이 적어 둔 그대로이고, 이번 조사에서도
공개 자료에서 채워지지 않았다:

```
① 요청 필드 / 필수값     — 87 등록 payload 와 같은 모양인가, 부분 전송인가
② 덮어쓰기 규칙          — 보내지 «않은» 칸은 유지되는가, 지워지는가
③ 되돌림 수단            — 실패·오적용 시 복구 경로
```

🔴 **②를 모르는 채로 PUT 하는 것이 이 조사가 막는 바로 그 일이다.** 부분 전송인 줄
알고 상품명만 보냈는데 전체 교체였다면, 보내지 않은 89개 칸이 비워진다.

## 3. 🟢 이번에 «새로» 알게 된 것 (94 실측, 2026-09-29)

일회용 읽기 전용 probe 로 93·94 를 실행해 얻은 사실 — 토큰·라우트는 폐기 완료.

```
94 요청   { trGrpCd, trNo, spdNo }          ← 그동안 기록 0 이던 모양
94 응답   returnCode 0000 · 최상위 90필드 · 등록에 보낸 값이 거의 그대로
          itmLst(단품 6: sitmNo·slPrc·stkQty·dpYn) · pdItmsInfo(고시 13) ·
          sftyAthnLst · epnLst · dcatLst · pdAprvStatInfo
```

**미지수 ①에 대한 부분 답**: 응답이 87 등록 payload 와 거의 같은 모양이므로,
90 의 요청도 그 모양일 «개연성» 이 높다. 🔴 개연성은 근거가 아니다 — 실측 전까지
UNKNOWN 이다.

**대상 상태(미지수 ①의 절반)는 풀렸다**: 우리 상품 2건이 `fnlAprvYn: "Y"`
(카테고리·상품정보 승인 둘 다 `APRV_CMPT`)다. 즉 **「승인 상품」 조건을 충족한다** —
90 의 대상이 되는 상태다. 그전까지는 「우리 상품이 90 대상인지」조차 몰랐다.

**되돌림 수단(미지수 ③)에 대한 사실**: 94 가 전 필드를 돌려주므로 **수정 전
baseline 을 완전히 확보할 수 있다.** 되돌리는 «행위» 는 여전히 90 을 한 번 더
부르는 것이고 그 계약이 미지수지만, 「무엇으로 되돌릴지」는 이제 안다.

## 4. 최소 변경 전략 (설계 — 실행 아님)

PUT 이 승인될 경우에 한해, 아래 순서를 벗어나지 않는다.

```
① 대상        LO2782636437 (dpYn="N" · 전시안함 · 고객 노출 0)
              🔴 전시 중인 LO2782615680 을 대상으로 삼지 않는다
② 사전        94 로 baseline 전문 확보 → 파일로 보존
③ 변경        상품명(spdNm) «한 칸». 그 외 어떤 칸도 값을 바꾸지 않는다
④ 전송        90. 요청 모양은 baseline 을 그대로 되보내는 형태로 시작한다
              (부분 전송이 아니라 전체 전송이 «보수적» 이다 — 덮어쓰기 규칙을
               모를 때는 「다 보내는」 쪽이 칸을 지우지 않는다)
⑤ 사후        94 재조회 → baseline 과 90필드 전수 대조
              🔴 상품명 외에 한 칸이라도 달라졌으면 그것이 이 실측의 결과다
⑥ 복구        달라진 칸이 있으면 baseline 값으로 90 을 한 번 더 부른다
⑦ 판정        대조 결과를 근거로 capability 를 정한다. 그 전에는 UNKNOWN 유지
```

🔴 **데이터 복구 가능성**: ②의 baseline 이 있으면 ⑥으로 되돌릴 수 있다. 단
**되돌림 자체가 90 이므로, 90 이 파괴적이면 복구도 파괴적이다.** 그래서 대상이
전시안함 상품이어야 한다 — 최악의 경우에도 고객 노출이 없다.

🔴 **옵션(itmLst)은 이 실측에서 손대지 않는다.** 옵션값·옵션명은 문서가 수정
불가라고 적었고, 가격·재고는 별도 API(91/86)다.

## 5. 지금 상태에서 하지 않는 것

* `EDIT_ADAPTERS` 에 롯데ON 을 **적지 않는다**. 적는 순간 화면이 「수정할 수
  있다」고 말한다 — `edit-adapters/index.ts` 주석이 이미 이 규칙을 적어 두었고,
  「문서에 API 가 있다」는 capability 근거가 아니다.
* `CHANNEL_CAPABILITY.lotteon.update` 는 **`UNKNOWN` 유지**. 따라서 기존 상품이
  연결돼 있으면 `resolveLifecycle` 이 `BLOCKED` 로 세우고, **CREATE 로 우회하지
  않는다**(그 판정은 이미 테스트로 고정돼 있다).
* 90/91/86/92/111 중 **어떤 것도 호출부를 만들지 않는다.**

## 5-B. 91 · 86 · 92 / 111 — 각각 조사한 결과 (CPO ④)

| apiNo | 기능 | 엔드포인트 | 공개 자료로 확인된 것 | 미확인 |
|---|---|---|---|---|
| 91 | 가격 변경 | `/product/v1/item/price/change` | 경로 · **단품(item) 단위** 라는 것 | 요청 필드 · 필수값 · 승인 상태 제약 |
| 86 | 재고 변경 | `/product/v1/item/stock/change` | 경로 · **단품 단위** | 〃 |
| 92 | 상품 판매상태 변경 | `/product/v1/product/status/change` | 경로 · 상품 단위 · 87 의 «되돌림 수단» 으로 문서에 기록돼 있음 | 요청 필드 · 전이 가능한 상태쌍 |
| 111 | 단품 판매상태 변경 | `/product/v1/item/status/change` | 경로 · 단품 단위 | 〃 |

🔴 **셋 다 90 과 «다른 축» 이다.** 경로가 `item/…` 인 둘(91·86)은 단품 단위라
`sitmNo` 가 키일 것으로 보이고, 94 응답의 `itmLst[].sitmNo` 가 그 값을 이미 준다.
🔴 그러나 **요청 필드가 확인되지 않았다.** 구현하지 않는다.

🟢 **설계상 중요한 사실 하나**: 가격·재고가 90 이 아니라 별도 API 라는 것은,
**「상품명만 고치는 90」이 가격·재고를 건드릴 «구조적 경로가 없다»** 는 뜻이다.
쿠팡에서 전체 교체가 27칸을 지울 수 있었던 것과 성격이 다르다.

## 5-C. Adapter 추가 가능 여부 판단 (CPO ⑥)

**결론: 아직 추가하지 않는다.** 판단 근거는 셋이다.

```
① EDIT_ADAPTERS 의 규칙 — 「읽고 고칠 수 있는지 확인된 뒤」에 한 줄이 는다
   읽기(94)는 확인됐다. 고치기(90)는 확인되지 않았다 → 절반이다
② 어댑터를 적으면 화면이 「수정할 수 있다」고 말한다. 눌렀을 때 일어나는 일이
   미확인인 상태에서 그 문장을 띄우지 않는다(쿠팡에서 가드 22개가 잡은 그 상태)
③ 지금 적어도 «고칠 수 있는 축이 0개» 다 — updateFields 에 넣을 이름이 없다
```

🟢 **다만 남은 작업량은 작다.** 94 가 baseline 을 주므로, 90 의 요청 규격만
확정되면 쿠팡 어댑터(`edit-adapters/coupang.ts`)와 **같은 모양**으로 붙는다 —
Core·Master·EditGate 는 한 줄도 바뀌지 않는다. 그 구조는 이미 테스트가 지킨다.

## 7. 🔴 94 응답 90필드 분류 (CPO 1단계)

분류 기준을 «의견» 이 아니라 **우리 코드** 로 잡았다 — `LotteOnProductRegistration`
(87 등록 타입, 59필드)과 94 응답(90필드)을 기계적으로 대조했다.

| | 개수 | 뜻 |
|---|---|---|
| **A. 87 ∩ 94** | **56** | 롯데ON 이 «등록 때 받고 조회 때 돌려주는» 칸 → 수정 가능 후보 |
| **B. 94 에만** | **34** | 우리 빌더가 보낸 적 없는 칸 — 롯데ON 이 채웠다 |
| **C. 87 에만** | **3** | 94 가 «안 돌려주는» 칸 |

### C — 🔴 가장 위험한 셋 (3개)

```
optSrtLst · prstMsgPsbYn · prstPckPsbYn      (옵션정렬 · 선물메시지 · 선물포장)
```

**94 baseline 만 되보내면 이 셋이 요청에서 빠진다.** 90 이 전체 교체라면 지워지거나
기본값으로 덮인다. 🟢 완화 가능하다 — 87 빌더가 무엇을 보냈는지 우리가 안다
(`prstPckPsbYn:"N"` · `prstMsgPsbYn:"N"` · `optSrtLst` 는 옵션이 있을 때만).
그래서 전송본은 **94 값 + 이 셋의 우리 등록값** 이어야 한다.

### B — 되보내면 «거절될» 칸과 그냥 설정인 칸이 섞여 있다

🔴 **보내면 안 될 것(롯데ON 이 관리하는 상태·식별자)**

```
spdNo          대상 지목 키다. 본문 필드가 아니다
pdAprvStatInfo 승인 상태(2단계) — 우리가 정할 값이 아니다
slStatCd · slStatRsnCd   판매상태 — 92/111 의 소관이다
epdNo          우리가 안 보내서 null 로 온다
saveTypCd · pdNm         저장구분 · 파생 상품명(spdNm 과 별개로 온다)
```

🟡 **의미 불명 — 우리가 쓰지 않는 부가기능(27개)**

```
adtnPdInfo · bookCultCstDdctYn · brkHmapPkcpPsbYn · crdayDvInfo · crdayDvPsbYn ·
cshbltyPdYn · cstAdtnLst · ctrtTypCd · dlcrtYn · echgPsbYn · ecpnInfo · gftvShpCd ·
```

렌탈·도서·쿠폰·당일배송·온누리상품권 같은 축이다. **우리가 값을 지어낼 수 없고,
94 가 준 값을 그대로 되보내는 것 외에 할 수 있는 일이 없다.**

### 🔴 그래서 「상품명 한 칸만 바꾸니 안전하다」는 성립하지 않는다

바꾸는 칸이 하나여도, **함께 실리는(또는 빠지는) 칸이 89개**다. 위험은 변경
필드 수가 아니라 **전송본 전체**가 결정한다. CPO 지적 그대로다.

## 8. 🟢 그래서 첫 실측은 «아무것도 바꾸지 않는» 요청이어야 한다

위 분류에서 나온 결론이고, 이것이 이 문서의 가장 중요한 변경이다.

```
1차 — NO-OP 실측
  전송본   94 baseline + C 3필드(우리 등록값) − B 의 상태·식별자 6필드
  spdNm    🔴 «현재 값 그대로». 한 글자도 바꾸지 않는다
  기대     성공하면 = 전체 교체여도 결과가 지금과 같다(멱등)
           거절되면 = 스키마를 배운다. 상품은 그대로다
  대조     실행 전후 94 를 90필드 전수 비교
```

🔴 **1차가 「성공 + 90필드 전부 동일」이어야만 2차로 간다.** 그때 비로소
「이 전송본은 이 상품을 바꾸지 않는다」가 실측으로 증명되고, 그 위에서 상품명
한 칸을 바꾸는 것이 처음으로 «한 칸짜리 변경» 이 된다.

```
2차 — 상품명 한 칸 (1차 통과 후에만)
  1차와 동일한 전송본에서 spdNm 만 교체 → 94 재조회 → 89필드 불변 + 1필드 변경 확인
```

### 복구 가능 범위 — 정직하게

| | |
|---|---|
| 🟢 복구 가능 | A·C 필드가 달라진 경우 — baseline 값으로 90 재호출 |
| 🟡 조건부 | B 의 부가기능 필드 — 94 가 준 값이 있으면 되보낼 수 있다 |
| 🔴 **복구 불가** | 90 이 «승인 상태» 를 되돌리는 경우(재승인 대기로 떨어짐). 승인은 롯데ON 심사라 우리가 되돌릴 수 없다 |
| 🔴 **복구 불가** | 옵션(itmLst) 구조가 바뀌는 경우 — 옵션값·옵션명은 «수정 불가» 라고 문서가 적었다 |

🔴 **그래서 1차 NO-OP 이 필요하다.** 위 두 「복구 불가」는 변경 여부와 무관하게
«90 을 한 번 부르는 것» 만으로 일어날 수 있고, NO-OP 이 그것을 가장 싸게 드러낸다.

### 🔴 「상품을 바꾸지 않고」 확인할 방법은 없는가

없다. 검토한 대안과 기각 사유:

```
dry-run 파라미터      문서에 없다
빈 요청(spdNo 만)     90 이 전체 교체면 «전 필드를 지우는» 요청이 된다. 최악
일부러 잘못된 요청    거절은 배우지만, 부분 적용 가능성을 배제할 수 없다
새 상품 만들어 시험   CPO 금지(외부 상품 추가 등록)
```

1차 NO-OP 이 **남아 있는 것 중 가장 덜 위험한 방법**이다 — 성공해도 결과가
현 상태와 같기 때문이다.

## 9. 🔴 94 비교로 «증명되는 것» 과 «증명되지 않는 것» (CPO 4항)

이 분리가 이번 검토의 결론을 정한다.

### 🟢 전후 94 비교로 검출 가능

```
A·B·C 90필드의 값 변화        전수 대조로 잡힌다
승인 상태 변화                 94 가 pdAprvStatInfo 를 돌려준다 —
                               catAprvStatCd · pdInfoAprvStatCd · fnlAprvYn
옵션 구조 변화                 itmLst 의 sitmNo 목록·개수
전시/판매 상태                 dpYn · slStatCd
```

🟡 **그러나 「검출 가능」은 「예방 가능」도 「복구 가능」도 아니다.** 94 는 90 을
«부른 뒤» 에만 답한다.

### 🔴 호출 자체의 부작용 — 비교로는 증명할 수 없다

```
롯데ON 내부 심사 큐에 재심사 건이 생겼는가        94 에 나오지 않는다
수정 이력이 이후 심사에 영향을 주는가             〃
승인 심사에 걸리는 시간 동안의 판매 가능 여부      〃
```

### 🔴 그리고 «검출돼도 되돌릴 수 없는» 것이 있다 — 공식 매뉴얼 확인

롯데ON 판매자 매뉴얼·가이드 원문에서 확인됐다:

```
「판매종료 처리 후 상태 변경이 불가능합니다」
   → 판매종료한 상품을 다시 팔려면 «신규상품 등록» 해야 한다
「기존 등록된 단품의 옵션, 옵션값은 수정이 불가」
「옵션정보를 '-' 버튼으로 삭제할 경우 다시 추가가 불가능」
「승인반려된 상품은 수정 후 재등록이 불가능」 → 반려사유 확인 후 새로 등록
```

🔴 **마지막 줄이 가장 무겁다.** 90 호출이 상품을 반려 상태로 보내면, 복구 수단이
**「새로 등록」** 이다 — 그것은 곧 중복 상품 하나가 더 생긴다는 뜻이고, 우리가
`c4b5eea`·`96eea77` 에서 막 고친 바로 그 사고다.

## 10. 🔴 결론 — 실측을 중단하고 CREATE 전용으로 유지한다 (CPO 5항)

CPO 승인 기준 셋에 대한 정직한 답:

| 기준 | 답 |
|---|---|
| ① 누락·오전달 필드가 기존 상품을 손상시키지 않는다는 근거 | ❌ **확보 못했다.** 90 의 전체 요청 스키마와 생략 필드 처리가 공개 자료에 없다 |
| ② 승인 상태·옵션 구조 영향을 확인할 수 있는 근거 | 🟡 **검출은 가능**(94 의 `pdAprvStatInfo`·`itmLst`). **예방·복구는 불가** |
| ③ 실패·부분 반영 시 복구 가능 범위 | 🟡 A·C 필드는 복구 가능. 🔴 **옵션 삭제·판매종료·승인반려는 복구 불가** |

①이 미충족이므로 **실측하지 않는다.** ②③의 「검출은 되지만 되돌릴 수 없다」는
조합은, 실측이 실패했을 때 남는 것이 «정보» 뿐이고 «상품» 은 잃는 구조다.

### 그래서 지금 확정하는 것

```
롯데ON   CREATE 전용. UPDATE 는 UNKNOWN 이고 화면이 그 사실을 말한다
         (resolveLifecycle 이 BLOCKED 로 세우고 CREATE 로 우회하지 않는다)
기존 상품 개선   스마트스토어·쿠팡 두 채널로 운영한다 — 둘 다 검증돼 있다
```

🔴 **포기가 아니라 «닫아 두는» 것이다.** 재개 조건은 하나뿐이고 분명하다 —
**90 의 공식 요청 스키마(필드 목록·필수값·생략 처리)를 확보하는 것.** 그 문서는
롯데ON API 센터의 판매자 로그인 뒤에 있고, 비밀이 아니라 «필드 목록» 이다.
셀러 계정으로 그 페이지를 열어 규격을 확보하면 그날 재개할 수 있다.

## 6. 승인 요청 — 🔴 **철회했다**

이 절은 원래 「PUT 1회 승인」을 요청했다. §9·§10 의 검토 결과로 **CTO 가
스스로 철회한다.** 승인 기준 ①(누락 필드가 상품을 손상시키지 않는다는 근거)을
확보하지 못했고, 실패했을 때 잃는 것이 «정보» 가 아니라 «상품» 이기 때문이다.

재개 조건은 §10 에 하나로 적혀 있다 — **90 의 공식 요청 스키마 확보.**
