## 🔵 결론 한 줄 — **영역마다 다르다. 브랜드는 구별되고 품번은 구별되지 않는다.**

```
🟢 BRAND        구별된다      추출 실패 3 : 실제 부재 5 (분모 8)
🔴 MODEL_CODE   구별 안 된다  구분 불가 3 : 실제 부재 5 (분모 8)
🟡 PRODUCT_NAME 질문이 거의 안 생긴다  분모 밖 2 · 원상품↔후보 불일치 6
🟢 DESCRIPTION  원문 수집은 성공  확보 8/8 · 그중 인코딩 손상 1
```

🔴 그리고 **새 상태를 추가하지 않아도 지금 구별이 된다** — 필요한 것은 **관찰 축 하나**
(「원문에 기준값이 실재하는가」)이고 그 함수는 **이미 운영 코드에 있다**(§7).

## §1. 네 영역의 실제 추출·관측 경로 — 🟢 코드에서 확정(추정 0)

owner 는 **`product-evidence.ts` 의 `extractProductEvidence`** 하나다. 입력은 **`title` 과
`description` 두 원문** 뿐이고 HTML 을 보지 않는다.

| 영역 | 생산 규칙(코드 그대로) | 읽는 원문 |
|---|---|---|
| **BRAND** | `lookupBrandByAliasInTitle(title)` · `BRAND_LABEL_RE.exec(desc)` · `lookupBrandByAliasInTitle(desc)` | TITLE · DESCRIPTION |
| **MODEL_CODE** | `extractDetailModelCodes(desc)`(승인 패턴 `\bB\d{3}[A-Z]{2}\d{3}\b` **하나**) · `extractLabeledProductCode(desc)` | DESCRIPTION |
| **PRODUCT_NAME** | `PRODUCT_NAME_LABEL_RE.exec(desc)` + 제목 원문 | TITLE · DESCRIPTION |
| **DESCRIPTION** | 🔴 **축이 아니다** — `const desc = input.description` 즉 **다른 셋의 입력** | — |

🔴🔴 **BRAND 축의 병목이 여기서 확정된다** — `lookupBrandByAliasInTitle` 은 등록부의
**`alias` 칸만** 본다. 등록부는 **브랜드 4개**(`Pèpè Shoes`/페페 · `Emile et Ida`/에밀에이다 ·
`Konges Slojd Clothing`/콩제슬래드 · `Bobo Choses`/보보쇼즈)이고 **alias 는 한글 표기** 다.
⟹ 🔴 **라틴 표기 `Bobo Choses` 가 원문에 있어도 그 함수는 찾지 못한다.**

🟢🟢 **그리고 두 칸을 다 보는 «관찰 전용» 함수가 이미 있다** — `findBrandAliasMentions`
(`brand-alias.ts:143` · BRAND-1 · 「alias 추가 0 · 새 사전 0 · 음역 추론 0」).
🔴 그 함수는 **운영 판정에 연결되지 않았고** 이 조사도 연결하지 않았다.

## §2. 상태별 정의와 실제 관측 사례

🔴🔴 **CPO ⑤ 를 둘로 갈랐다 — 내 1차 라벨이 거짓이었다.** 운영 `CONFLICT` 는
「**원상품 ↔ 후보** 값이 호환 안 됨」이고, CPO ⑤(「복수 관측값이 충돌함」)는
「**한쪽 안에서** 값이 여러 개이고 서로 다름」이다. 🔴 한 라벨로 적으면 숫자가 조용히 틀린다.

| 라벨 | 정의 | 발생 조건 | 관측 |
|---|---|---|---:|
| `원문 있음 · 증거 실제 부재` | 원문이 있고 그 식별 정보가 **없다** | 원문 O · 재검색 **불발** | **10** |
| `원문 있음 · 증거 있음 · 추출 실패` | 원문에 **있는데** 관측·추출이 못 잡았다 | 원문 O · 재검색 **적중** · 축 비었음 | **4** |
| `원문 자체 없음` | 원문이 없거나 수집되지 않았다 | `title`·`desc` 둘 다 없음 | **0** |
| `미측정` | 그 영역을 재지 않았다 | 축 행 자체가 없음 | **0** |
| `원상품 ↔ 후보 값 불일치` | 양쪽 PRESENT · 호환 안 됨 | 운영 `CONFLICT` | **6** |
| `한쪽 내 복수 관측값 충돌` | 한쪽에 서로 다른 값이 둘 이상 | `origin`/`candidate` 고유값 ≥2 | **0** |
| 🔴 `구분 불가(미확정)` | 판정 불가 — 추정으로 채우지 않는다 | 아래 §3-B | **3** |
| `해당 없음(분모 밖)` | 축이 이미 `PRESENT` · 또는 그 영역이 「원문 수집 여부」 자체 | — | **9** |

### 🟢 「추출 실패」로 분류한 넷 — **원문 발췌를 같이 적는다**(「포함」만 쓰지 않는다)

```
BRAND  junioredition.com  ← TITLE+DESCRIPTION
       「Bobo Choses Pop Sweatshirt by Bobo Choses」
BRAND  kids-world.com     ← TITLE+DESCRIPTION
       「Bobo Choses 맨투맨 - 미드나잇 블루 포함 프린트」
BRAND  coupleshot.com     ← DESCRIPTION
       「[?????,BOBO CHOSES Bobo Choses Pop sweatshirt ???Ʈ???(?」   🔴 인코딩 손상
DESCRIPTION coupleshot.com ← DESCRIPTION   🔴 같은 손상(원문은 확보됐다)
```
🔴 앞의 둘은 **표기 체계 문제**(등록부 `alias` 칸만 보는 구조) · 셋째는 **인코딩 손상** 이다.
🔴 **coupleshot 은 관측 사례 하나** 다 — 일반 실패 유형으로 **확대하지 않는다**(CPO 명시).

### 🔵🔵 교차 사실 — **추출 실패가 걸린 곳이 「동일상품」 쪽이다**

```
CEO 확인(🟢 거처 = **CPO 작업지시서 기록** · MIER-01 §5 가 받아 적은 값)
  SAME            junioredition.com · kids-world.com
  추가 확인 필요   coupleshot.com
  DIFFERENT       나머지 5
🟢 BRAND 추출 실패 **3건이 정확히 그 셋** 이고, 실제 부재 5건은 **DIFFERENT 5건과 정확히 일치** 한다
🔴🔴 **N=8 로 인과를 단정하지 않는다** — 「그 분류가 CEO 판단과 어긋나지 않았다」까지다
🔴🔴 **라벨의 거처를 섞지 않는다** — `candidate_reviews.human_verdict` 는 **10/10 null**
   (실측). 「DB 에 CEO 라벨이 있다」로 적지 않는다.
```

## §3. 현재 구조로 구분 가능한 경우와 불가능한 경우

### 🟢 A. 구분 **가능** — BRAND

판별식은 둘의 **차이** 다(둘 다 지금 있는 것이다):
```
운영 축     lookupBrandByAliasInTitle  → 등록부 **alias 칸만**
관찰 전용   findBrandAliasMentions     → 등록부 **alias + brand 두 칸**
⟹ 「관찰은 찾는데 축은 비었다」 = **추출 실패**        (3건)
   「둘 다 못 찾는다」            = **증거 실제 부재**  (5건)
```
🟢 그리고 그 5건은 **구조화 브랜드가 서로 다른 실제 브랜드** 다(FENDI · Gray Label ·
Lacoste · Petite Maison Kids · Piccoli & Co™) ⟹ 🟢 **지금 판정이 정확하다.**

### 🔴 B. 구분 **불가능** — MODEL_CODE (3건)

```
junioredition · kids-world · coupleshot
  후보 쪽 축 상태   PRESENT (후보가 `B226AC033` 을 적었다 · source **DESCRIPTION**)
  비교 상태         **MISSING**
  원인              🔴 **원상품 쪽 관측이 비어** comparison 이 MISSING 이 된다
⟹ 🔴 그 MISSING 은 **후보의 추출 실패가 아니다.** 「후보 추출 실패」로 적으면 거짓이다
⟹ 🔴 그래서 `구분 불가(미확정)` 로 적었다 — 추정으로 채우지 않는다
```
🔵 **구별하려면 「어느 쪽이 비었는가」를 봐야 한다.** 그 정보는 **이미 응답에 있다**
(`originState` / `candidateState` 가 따로 온다) ⟹ 🟢 **새 상태가 아니라 «읽는 방법» 문제** 다.

### 🟡 C. 질문이 거의 생기지 않음 — PRODUCT_NAME

제목은 **8/8 확보** 돼 있어 「원문 없음」이 0 이다. 분모에 남는 것은 **원상품↔후보 불일치
6건** 이고 그것은 실패/부재가 아니라 **다름** 이다(그중 **다국어 1건** = kids-world).

### 🟢 D. 원문 수집 축 — DESCRIPTION

**8/8 확보**(136~2,010자) · `원문 자체 없음` **0** · 🔴 **인코딩 손상 1건**.
🔵 즉 이 영역의 실패는 「받지 못했다」가 아니라 **「받았는데 읽을 수 없다」** 다.

## §4. 신규 상태 제안 및 오분류 위험

🔴🔴 **CTO 권고는 「새 상태를 운영 타입에 추가하지 않는 것」이다.** 이유 셋:

```
① 🟢 구별에 필요한 정보가 **이미 응답에 있다** — originState/candidateState 분리 ·
   structured 세 칸(UIED-02) · description 원문(UIED-02)
② 🔴 「추출 실패」는 **축의 상태가 아니라 «대조 결과»** 다 — 원문 재검색이라는
   **다른 관측** 이 있어야 성립한다. 축 타입에 넣으면 축이 자기 입력을 넘어선다
③ 🔴 그리고 오분류 위험이 **비대칭** 이다(아래)
```

그래도 CPO 가 요구한 꼴로 **제안만** 적는다(🔴 운영 타입에 넣지 않았다):

| 명칭(제안) | 정의 | 발생 조건 | 🔴 판정 불가 조건 |
|---|---|---|---|
| `EXTRACTION_FAILED` | 원문에 기준값이 실재하는데 축이 비었다 | 원문 O **AND** 관찰 전용 재검색 적중 **AND** 그 축 `originState`/`candidateState` 가 그쪽에서 비었음 | 🔴 원문이 없을 때 · 🔴 **반대쪽** 이 비어 comparison 만 MISSING 일 때 · 🔴 기준값이 없을 때(원상품 브랜드/품번 공백) |
| `SOURCE_UNREADABLE` | 원문은 받았는데 읽을 수 없다 | 치환문자·제어문자 비율 > 2% | 🔴 비율 임계값은 **N=1 로 고정하지 않는다**(아래 위험 ③) |

### 🔴 오분류 위험 넷 — 전부 **실측에서 나온 것** 이다

```
① 🔴🔴 **「비교 상태 MISSING」을 「후보 추출 실패」로 읽는 위험**
   실측 3건이 그 모양이고, 실제로는 **원상품 쪽이 비었다**. 가장 큰 위험이다
② 🔴 **관찰 전용 재검색이 등록부에 묶여 있다** — `findBrandAliasMentions` 도 등록부
   **4 브랜드** 안에서만 찾는다 ⟹ 등록부 밖 브랜드는 **「실제 부재」로 오분류** 된다
   (이 표본의 FENDI·Lacoste 등 5건은 「부재」가 맞지만, **그것이 등록부 밖이기 때문** 인지
    **정말 없기 때문** 인지 이 데이터로는 가르지 못한다 ⟹ 🔴 **미확정**)
③ 🔴 **인코딩 임계값 2% 는 1건에서 고른 값** 이다 — 전수 빈도 **미측정** ⟹ 정책 금지
④ 🔴 **「추출 실패」라벨이 SAME 근거로 새는 위험** — 실측에서 그 3건이 전부 CEO SAME/
   추가확인 쪽이라 **상관이 보인다**. 🔴 그래서 **표시/분류 전용 경계를 계약으로 잠가야** 한다
```

## §7. 다음 단계 최소 변경안 — 🔴 **별도 승인 사안**

🔵 **CTO 권고 — 새 상태보다 「읽는 방법」이 먼저다.** 비용 순으로 셋:

| 순위 | 최소 변경안 | 범위 | 🟢 효과 | 🔴 별도 승인 필요 |
|---|---|---|---|---|
| **1** | 🟢 **변경 0** — 화면/조사에서 `originState`/`candidateState` 를 **갈라 읽는다** | 코드 **0**(응답에 이미 있다) | §3-B 의 「구분 불가 3건」이 **즉시 구분된다**(어느 쪽이 비었는지 보인다) | 🟢 없음 |
| **2** | 관찰 전용 재검색을 **증거 응답에 한 칸** 추가 (`observedInText: { found, where, excerpt }`) — owner 는 **기존 `findBrandAliasMentions`** | 응답 칸 1 · schema **0** · 운영 1 파일 | BRAND 「실패 ↔ 부재」가 **응답에서 구분된다**(3 : 5) | 🔴 소비처 비개입 계약 필수 · 🔴 **등록부 밖 브랜드는 여전히 구분 불가** 를 같이 표시해야 한다 |
| **3** | `SOURCE_UNREADABLE` 관찰 칸 | 응답 칸 1 | 인코딩 손상을 `MISSING` 에서 분리 | 🔴🔴 **임계값 근거가 1건** ⟹ 전수 빈도 측정이 **선행** |

🔴 **셋 다 새 운영 «상태 타입» 을 만들지 않는다** — ②③은 **관찰 칸** 이고 `comparison`
값은 넷 그대로다. 🔴 그리고 **MODEL_CODE 의 구분 불가는 ②로 해결되지 않는다**(원인이
원상품 쪽 공백이고, 그 공백을 메우는 것은 **WU-080 에서 CPO 가 REJECT 한 축** 이다).

🔴 **하지 않을 것** — 새 상태를 운영 타입에 추가 · 등록부 alias 무차별 확장 ·
인코딩 복원(추정) · 상세설명을 SAME 근거로 연결 · 임계값/판정 정책 변경 ·
coupleshot 1건으로 추출 구조 변경.
