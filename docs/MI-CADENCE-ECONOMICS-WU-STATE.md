# MI Re-observation Cadence & Economics WU

> 🟢 **종료.** 판정은 §6 — **GO · 권장 주기 2~3일**(🔴 「Cron 개발 GO」가 아니다).
> 🔴 **Production 0 · cron 미구현 · 새 HTTP 0.** DB 는 SELECT 만.
> 🟢 선행 위치: `Re-observation Value WU = GO CANDIDATE`(`docs/MI-REOBSERVATION-WU-STATE.md`).

---

## 1. Strategic Question

> 1일 / 2일 / 3일 / 7일 중 **사업적으로 최적인 관측 주기**는 무엇인가.
> (추가 관측 비용 → 추가로 발견되는 의미 있는 변화 → Seller Intelligence 가치)

---

## 2. 🔴🔴 측정 가능성을 «먼저» 갈랐다

이것을 안 가리면 숫자가 외삽이 된다.

```
🟢 잴 수 «있는» 것 — **다운샘플링**
   실제 관측 시계열을 K일 간격으로만 봤다고 가정해 «무엇을 놓치는가» 를 센다.
   데이터 «안에서만» 움직인다.
🔴 잴 수 «없는» 것 — 「지금보다 더 촘촘히 봤다면 무엇을 더 찾았을까」
   데이터에 없는 관측을 가정하는 **상향 외삽** → **측정불가**.
   ❗ 그래서 이 WU 가 답하는 질문은 정확히
     **「1일에서 2/3/7일로 «늦추면» 무엇을 잃는가」** 다.
```

### 🔴 해석 함정 — 실제로 빠질 뻔했다

간격별 변화율(실측): `1일 224쌍/42.4% · 2일 16/81.2% · 3일 12/100% · 6일 14/57.1%`

🔴 **이 표를 주기 선택 근거로 단독 사용하면 틀린다.** 간격이 길수록 변화율이
오르는 것은 당연하고(더 기다리면 변할 확률이 높다), 더 중요하게는 —
**가격이 변했으면 2일 뒤에 봐도 여전히 다르다.** 늦게 봐도 같은 변화를 놓치지
않는다.

🟢 주기가 실제로 결정하는 것은 **둘** 이다:
```
① 지연        변화를 며칠 늦게 아는가
② 비가역 손실  올랐다 되돌아간 가격 상태를 **영구히 못 보는가**
```
→ 이 WU 는 그 둘을 센다. ②가 cadence 의 **유일한 비가역 손실** 이다.

## 3. 분모 (FULL POPULATION · 운영 멱등과 같은 해상도로 접었다)

```
SELLER_ORIGIN 관측 1476행 / 스냅샷 397개
🔴 분모(관측 2일+ 상품)  **93**
🔴 연속 관측 쌍           **271**
🔴 편중 — 상위 5개 상품이 만든 쌍  39/271 (**14.4%**)  → 🟢 심하지 않다
🔴 해상도 상한 「일」 — hasObservationToday(run-price-check.ts:242) 가 하루 1회로
   묶는다. **1일보다 짧은 주기는 무의미** 하다(코드가 버린다).
```

🟢 **날짜 대표 1건으로 접었다** — 운영 멱등과 같은 규칙이다. 같은 날 중복 행
(207그룹, 최대 8행)이 주기 계산을 오염시키지 않게 한다.

## 4. 주기별 손실 — 다운샘플링 (sample N=93 상품 / 271쌍)

| 주기 | 관측수 | 비용비 | 변화 검출 | **변화 상품** | 유지율 | 평균 지연(일) | 🔴 비가역 손실 | 구별 상태 |
|---:|---:|---:|---:|---:|---:|---:|---:|---:|
| **1일** | 364 | 100.0% | 150 | **51** | 100.0% | 0 | **0** | 236 |
| **2일** | 211 | 58.0% | 96 | **48** | **94.1%** | 0.08 | 46 | 190 |
| **3일** | 172 | 47.3% | 68 | **43** | 84.3% | 0.49 | 74 | 162 |
| **7일** | 121 | 33.2% | 27 | **24** | 47.1% | **2.96** | 115 | 121 |

🔴 지연 측정 분모는 각각 51 / 48 / 43 / 24 다(변화가 있던 상품 수).

### 🟢 비용 대비 가치 — 효율 = 변화 상품 / 관측수

```
1일  0.140   (기준)
2일  0.227   **1.62x**
3일  0.250   **1.78x**   ← 🟢 최고
7일  0.198    1.42x
```

### 🔴 늦추면 무엇을 잃는가 (CPO 가 요구한 형태)

```
1일 → 2일   비용 **42% 절감**  ↔  변화 상품 **3개(6%)** 손실 · 지연 0.08일
1일 → 3일   비용 **53% 절감**  ↔  변화 상품 **8개(16%)** 손실 · 지연 0.49일
1일 → 7일   비용 **67% 절감**  ↔  변화 상품 **27개(53%)** 손실 · 지연 **2.96일**
```

🟢 **CPO 가설이 데이터로 지지된다** — 「1일은 비용만 2배인데 정보 증가가 거의 없다」.
1일 대비 2일은 비용이 **42% 싸고** 변화 상품은 **6%만** 잃는다.
🔴 반대로 7일은 변화 상품의 **절반(53%)** 을 잃고 지연이 **3일**이다 → 너무 느리다.

### 🔴 비가역 손실은 2일에서도 생긴다 (0 이 아니다)

```
구별되는 가격 상태  1일 236 (전부) → 2일 190 · 3일 162 · 7일 121
→ 2일 주기도 **46개 가격 상태를 영구히 못 본다**
실례  Booty Ghosts T-Shirt  3일 관측 → 2일 주기로 보면 70,300 을 못 본다
      Lulu T Bar Shoes      4일 관측 → 2일 주기로 보면 226,000 을 못 본다
```
🔴 즉 **2일은 「무손실」이 아니다.** 「변화 상품 94% 유지」와 「가격 상태 80% 유지」를
같은 숫자로 쓰지 않는다.

## 6. 판정 — **GO · 권장 주기 2~3일**

```
🟢 GO 근거
  ① 1일은 비용 대비 비효율 — 2일이 비용 58%에 변화 상품 94% 를 지킨다
  ② 7일은 NO — 변화 상품 53% 손실 · 지연 2.96일
  ③ 효율 최고는 3일(1.78x), 안전 최고는 2일(유지율 94.1%)
  🔴 둘 중 선택은 **비용 금액**에 달렸고 그 숫자는 측정불가다 → CPO/CEO 결정

🔴 「Cron 개발 GO」가 아니다. 이 WU 는 **주기 숫자** 를 정한 것이다.
   cron 구현은 별 Production WU 이고, 그 전에 선행조치 둘이 남아 있다(§7).
```

### 🔴 2일 ↔ 3일 선택 기준 (CPO 가 결정할 한 줄)

```
비용이 제약이면      → **3일** (월 4,970회 · 효율 1.78x · 유지율 84%)
정확도가 제약이면    → **2일** (월 7,455회 · 효율 1.62x · 유지율 94%)
🔴 1일과 7일은 둘 다 탈락이다.
```

```

   🔴 자동화하면 이 거짓 신호도 «같이» 늘어난다. 제품 정책 경계(문구 표현).
② 과거 혼재 스냅샷 4건 — 새 행이 붙으면 거짓 알림이 다시 날 수 있다.

🔴 §10 Historical Data Integrity Risk 를 이 WU 의 가치 숫자와 **합산하지 않았다.**
```

## 8. 최종 보고 전 Numeric Gate

```
① 전수 vs 표본
   🟢 전수 — SELLER_ORIGIN 1476행 / 397 스냅샷 / 연속 쌍 271 / 간격 분포
   🔴 표본 — 주기별 표는 `sample N=93`(관측 2일+ 상품만). 전수 497 로 일반화 금지
   🔴 비용표는 전수 497 «가정» 이다 — 관측 실적이 아니라 **계획 수치** 다
② 다음 단계 통과
   🟢 관측수 → 변화검출 → 변화상품 → 지연 → 비가역손실 을 각 주기마다 셌다
   🟢 정합성 가드 — 주기가 길어지면 관측수가 «줄어야» 한다(테스트로 잠갔다)
③ 0 / UNKNOWN / 측정불가
   🔴 1일의 «추가» 정보량 · 금액 비용 · latency · Availability 를 전부
      **측정불가** 로 적었다. 0 이나 성공/실패로 바꾸지 않았다
   🔴 「1일 관측에서 변화 0%」를 「가격이 안 변한다」로 쓰지 않았다(§2 함정 절)
```

   셀러 판단에 얼마나 영향을 주는지는 이 데이터로 알 수 없다
🔴 환율 기인 변화가 주기별로 어떻게 늘어나는지는 **분리 측정하지 않았다**
