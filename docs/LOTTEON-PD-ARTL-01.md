## 3. 🔴 그런데 — 제 이전 「확정」에 약점이 있다

P1-D 가 이렇게 닫았다(그리고 제가 그대로 인용해 왔다):

```
89 PD_ARTL_CD   ok:true · rowCount 0   → 고시 항목코드 조회 API 없음 (CONFIRMED)
```

**그 `PD_ARTL_CD` 라는 그룹 이름은 «우리가 지어낸 것»이다.**

```
apps/admin/src/app/api/lotteon/payload-preview/route.ts:194
  pdArtl: await probeCodeGroup("PD_ARTL_CD"),      ← 근거 없이 정한 이름
```

그렇다면 `rowCount 0` 은 두 가지 중 무엇인지 **구분되지 않는다** —

```
① 항목코드 어휘가 «없다»
② 그 이름의 그룹이 «없다» (이름이 다를 뿐 어휘는 있다)
```

🔴 이것은 제가 반복해서 스스로 금지해 온 오류와 같은 꼴이다 —
**「없음은 실행으로 확인한다」** 인데, 실행한 것은 «우리가 지어낸 이름» 이었다.

### 그리고 그것을 가를 공식 수단이 «이미 문서에 있다»

**API 88 「공통코드 그룹조회」**

```
GET /v1/openapi/bocommon/v1/code/getGroupCodeList
요청 파라미터  없음
응답          data[] { grpCd, grpCdNm, grpCdEpn },  dataCount 예시 = 150
```

파라미터가 없고 **전체 그룹 목록**을 준다. 즉 **추측 없이** 다음을 알 수 있다 —

- 항목코드에 해당하는 그룹이 실재하는가
- 실재한다면 그 **정확한 이름**은 무엇인가 (`PD_ARTL_CD` 가 아닐 수 있다)

우리 클라이언트에는 88 경로가 **없다**(`client.ts` 에 `detailCodeList`(89)만 존재).
**한 번도 부른 적이 없다.**

🔴 88 을 부르려면 읽기 전용 라우트 한 개가 필요하다 = **코드 변경**.
이번 작업지시는 코드 변경 0 이므로 **제가 만들지 않았다.** CPO 판단 사항으로 올린다.

## 4. 부수 발견 — 🔴 우리 문서가 틀렸다 (204)

공식 목록: **`204 = 브랜드 조회`**, `203 = 속성 기본 조회`.

그런데 우리 문서는 204 를 「속성모듈」이라 적고 이렇게 결론냈다 —

```
docs/COMMON-COMMERCE-AUTO-MAPPING-P0.md:47   ### 204 속성모듈 — 🔴 부르는 코드가 없다
docs/COMMON-COMMERCE-AUTO-MAPPING-P0.md:71   ❌ 204 없이는 brdNo ↔ 브랜드명 매핑 근거가 «전무» 하다
```

**이름부터 틀렸고, 결론도 따라서 틀렸다.** 204 는 실재하는 브랜드 조회 API 다:

```
GET https://onpick-api.lotteon.com/cheetah/econCheetah.ecn?job=cheetahBrnd
     mf_1     브랜드명 부분일치 필터
     filter_1 브랜드 ID
응답  브랜드 ID · 대표명 · 국문명 · 영문명 · 유형코드 · 로고 · 이명/키워드 변형
```

즉 「브랜드 자동 매핑 근거 전무」는 **사실이 아니었다.** 근거는 공식 문서에 있었다.
🔴 다만 이것은 별개 HOLD 항목이므로 **여기서 구현하지 않는다.** 보고만 한다.
