## P1-2. 택배사

### 세 채널이 각자 다른 «층» 에 저장한다

| 채널 | 공통에 저장된 것 | 형태 | payload | 변환 | 목록 API | 셀러 선택 | 증거 |
|---|---|---|---|---|---|---|---|
| Coupang | `deliveryCompanyCode` | 쿠팡 **코드** (`EPOST`) | `deliveryCompanyCode` | 없음 — 그대로 | ❌ 없음 | 1회(설정) | 코드 |
| SmartStore | `naverDeliveryCompanyCode` | **사람 이름** (`우체국택배`) | `deliveryCompany` | 없음 — 그대로 | ❌ 없음 | 1회(설정) | 코드 |
| LotteON | `courier_code` (067) | 롯데ON **코드** | `hdcCd` · `rtngHdcCd` | 없음 — 그대로 | ✅ **89 DV_CO_CD** | 1회(설정) | 코드 |

### 네 질문에 대한 답

**① `COMMON_CARRIERS` 에 롯데ON 열이 있는가 — 없다.**
그 이유가 표 안에 주석으로 남아 있다(주석 근거, `common-carrier.ts:24`):

> 🔴 롯데ON 칸을 «지어내지 않는다». 89(DV_CO_CD) 실응답을 본 적이 없고,
> 이름이 같다고 코드가 같다고 볼 근거가 없다.

**② 같은 축인가 — 아니다.** 세 곳에 따로 저장된다.

```
coupang_seller_profiles.delivery_company_code        쿠팡 코드
coupang_seller_profiles.naver_delivery_company_code  사람 이름
lotteon_seller_settings.courier_code (067)           롯데ON 코드
```

**③ 「우체국택배」 하나로 셋을 결정할 수 있는가 — 🔴 둘은 되고 하나는 안 된다.**

```
SmartStore  이름 그대로     → 결정 «가능»
Coupang     COMMON_CARRIERS 표에 coupang 열이 있다 → 결정 «가능»
LotteON     코드계를 모른다 → 89 실응답 없이는 «불가»
```

🔴 **여기가 이번 조사의 핵심 갈림길이다.** 롯데ON 만 못 하는 이유는 「코드체계가
달라서」가 아니라 **89 응답을 한 번도 본 적이 없어서**다. 89 가 `cdNm = "우체국택배"`
같은 이름을 준다면 **장소와 달리 이름이 곧 정체성**이므로 자동 대응이 가능하다.
그 판단은 실응답을 보고 한다 — 지금은 `UNKNOWN`.

**④ 반품 택배사를 별도 개념으로 갖는 채널 — 롯데ON 뿐이다.**

```
Coupang     반품 택배사 개념 없음
SmartStore  판매자센터 등록 목록의 «우선순위» 만 읽는다(returnDeliveryCompanyPriorityType)
LotteON     rtngHdcCd 를 출고와 «별도» 로 요구
```

🔴 따라서 공통에 「반품 택배사」 자리를 만드는 것은 **한 채널을 위해 Common 을
늘리는 것**이다. 기존 원칙과 부딪힌다 — CPO 판단 사항.

## P1-5. `epdNo` — 🔴 Case A 는 맞지만 «비교 대상이 틀렸다»

### 먼저 축을 바로잡는다

내 1차 감사가 `epdNo`(상품 단위)와 쿠팡 `externalVendorSku`(**단품** 단위)를
같은 것으로 놓고 비교했다. **층이 다르다.**

| 층 | SmartStore | Coupang | LotteON |
|---|---|---|---|
| **상품** | `originProduct.sellerManagementCode` ← `product.sku` **자동**(`:623`) | 🔴 **필드 자체가 없다** | `epdNo` ← **셀러 입력** |
| **단품** | `optionCombinations[].sellerManagerCode` ← `variant.sku` 자동(`:325`) | `items[].externalVendorSku` ← `variant?.sku ?? sku` 자동(`:1486`) | `eitmNo` ← `variant.sku ?? sku` **자동**(`:248,285`) |

🔴 **단품 층은 세 채널 모두 이미 자동이다.** 끊긴 곳은 **상품 층 하나**이고,
진짜 비교 대상은 **SmartStore `sellerManagementCode` 뿐**이다.
쿠팡은 「자동」이 아니라 **「개념이 없다」** — 이것을 「두 채널이 자동인데
롯데ON 만 묻는다」고 쓴 것은 과장이었다. 정정한다.

### 계약

```
의미        업체상품번호 — «우리 쪽» 식별자. 87 응답의 spdNo(판매자상품번호)와
            짝을 이룬다(types.ts:155, 문서)
필수 여부   ❌ 아니다 — 타입이 `epdNo?`, 검증기에 검사가 «없다»  (코드)
쓰임        등록 후 93 상품상태 조회의 질의 키
            (product-status/route.ts:42,72 — 최대 100개)
유일성      🟡 UNKNOWN — 문서 확인 필요. 「우리 쪽 식별자」이므로 우리 안에서
            유일해야 할 것으로 «보이지만» 롯데ON 측 제약은 확인 못 했다
길이/문자   🟡 UNKNOWN
등록 후 변경 🟡 UNKNOWN
생성 규칙   🔴 코드 주석은 「jobKey/sku 등에서 만든다」(build-payload.ts:118)
            — 그런데 «만드는 코드가 없다». 화면이 셀러에게 묻는다.
```

### 🔴 왜 중요한가 — 비어 있으면 잃는 것이 있다

`epdNo` 가 없으면 87 응답의 `epdNo/spdNo` 짝을 맞출 수 없고 93 상태조회의
질의 키가 사라진다. **필수가 아니라서 등록은 되지만, 등록 «뒤» 를 추적하지
못한다.** 화면 도움말도 그렇게 적혀 있다 — 「등록 후 상품 상태 조회(93)에 씁니다」.

### 판정

```
Case A 유지  ✅ 우리가 가진 식별자(sku/작업키)로 채울 수 있는데 셀러에게 묻는다
단, 자동화 전에 문서로 확인할 것: 유일성 · 길이/문자 · 등록 후 변경 가능 여부
🔴 SKU 를 그대로 쓸지 작업키를 쓸지도 그 확인 뒤에 정한다
   (같은 SKU 의 상품을 두 번 등록하면 어떻게 되는가 — 지금은 모른다)
```

## P1-3. 고시정보 — 🔴 **품목은 되고 항목은 «채널이 주지 않는다»**

### 네 질문

**① 고시 «품목» 목록을 API 로 받을 수 있는가 — ✅ 된다. 이미 운영 중이다.**

```
api/lotteon/common-codes/route.ts   89 getDetailCodeList · grpCd="PD_ITMS_CD"
주석 근거(route.ts:36)              「실측 확인(2026-09-22): 40건」
                                    🔴 규칙이 아니라 실제 응답을 보고 인정한 기록
증거 수준                           실응답(우리 기록)
```

**② 고시 «항목코드» 목록을 API 로 받을 수 있는가 — 🔴 없다.**

확인 방법(전수):

```
api/lotteon/ 아래 라우트 6개 전부    항목코드 조회 경로 «없음»
lotteon-category.ts (205/206 파싱)   품목코드는 읽는다 · 항목코드 구조 «정의 없음»
코드 전역 검색                        pdArtlCd 를 «조회» 하는 함수 없음
205 응답의 pd_itms_list              🟡 비어 있는 것으로 «보인다» — 실측 미확인
```

지금 방식: `parseNoticeArticles()` 가 셀러가 손으로 적은 `항목코드:내용` 텍스트를
줄 단위로 쪼갠다. **항목코드 유효성 검사는 없다** — 형식만 맞으면 그대로 나간다.

**③ 공통 → 고시 매핑이 가능한가 — 🟡 «내용» 은 이미 다 모아 놓았고, «코드» 가 없다.**

`collectLotteOnNoticeSourceValues(product)` 가 열한 가지를 모은다 —
소재 · 색상 · 치수 · 제조사 · 원산지 · 취급주의 · 권장연령 · 품명 · 모델명 ·
수입사 · KC 인증유형.

🔴 **그런데 화면에 「참고」로만 보여준다.** 고시 항목에 주입하지 않는다.
항목코드를 모르니 `코드:내용` 의 왼쪽을 채울 수 없기 때문이다.

**④ 셀러가 상품마다 입력해야 하는 것 — 항목코드 + 내용 조합.**

```
품목코드 pdItmsCd     카테고리를 고르면 205 가 함께 준다 → 자동
항목 pdItmsArtlLst    🔴 셀러가 「0020:파란색」 식으로 직접 적는다
```

### 왜 세 채널이 다른가 — 원인이 명확하다

| 채널 | 자동화 | 가능한 이유 |
|---|---|---|
| SmartStore | ✅ 전면 | 품목이 **WEAR/KIDS 두 종뿐** → 필드명을 고정할 수 있다 |
| Coupang | ✅ 부분 | **카테고리 메타에 필드 목록이 들어 있다** → 받은 스키마대로 매칭 |
| LotteON | 🔴 없음 | **품목별 항목 스키마를 주는 API 가 없다** |

🔴 즉 롯데ON 고시 미자동화는 **우리 게으름이 아니라 채널이 스키마를 주지
않는 것**이다. 그리고 그것을 확정하려면 **205 의 `pd_itms_list` 실응답**을
봐야 한다 — 비어 있는지, 케이싱이 다른지(`pd_Itms_list` vs `pd_itms_list`)
아직 구분되지 않는다(파서는 둘 다 읽게 방어돼 있다).

### 🔴 화이트리스트에서 나온 별건

`common-codes` 는 두 그룹만 통과시킨다 — `PD_ITMS_CD` · `OPLC_CD`.
화면이 부르는 것도 그 둘뿐이다(`:703`, `:716`). **막힌 곳은 없다.**

```
택배사 DV_CO_CD · 배송지역 DV_RGSPR_GRP_CD
  → common-codes 가 아니라 delivery-settings 라우트가 «직접» 89 를 부른다
  → 🔴 그 라우트가 방금까지 405 로 죽어 있었다(P0-1)
```

그래서 CEO 캡처의 「고시 품목코드 목록을 불러오지 못했습니다」는 **화이트리스트
문제도, 기능 부재도 아니다.** 2026-09-22 에는 40건이 왔다. 그 사이에 인증/IP/
거래처 조회 중 무엇이 바뀌었는지는 **실행으로만 확인된다.**
