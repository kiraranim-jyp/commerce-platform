## 1. 공식 고시 PDF — 전수 판독

```
https://s3.ap-northeast-2.amazonaws.com/doc-pub.lotteon.com/product/static/article/…pdf
15 페이지 · 379행(품목 01~40) · Excel 내보내기 · 표지·서문·후문 «없음»
```

| 확인 | 결과 |
|---|---|
| 일반 작성기준 절 | 🔴 **존재하지 않는다.** 1페이지 첫 줄이 표 헤더이고 15페이지는 표 중간에서 끝난다. 하이퍼링크 0개 |
| `필수여부` | 🔴 **379행 전부 `Y`** · `N` 은 0건 — **이 PDF 는 필수/선택을 구분하지 않는다** |
| `0220` 작성 가이드라인 | 🔴 **14개 품목 전부 공란** — 품목 23 만의 누락이 아니다 |
| `1830` | 품목 23 에만 1회. 「제한이 있는 품목의 경우 반드시 기재」가 전부 |
| 「해당없음」류 | **항목별로만** 지정 · `"해당없음"` / `"해당 없음"` / `"대상 아님"` 혼용. 🔴 품목 23 의 13행에는 **하나도 없다** |
| `0800` 항목명 | 🟢 「취급방법 및 취급시 주의사항, **안전표시** (주의, 경고 등)」 — 안전표시 포함 확정 |
| `0070` 구분자 | 🔴 **PDF 가 지정하지 않는다** — 우리가 정한 `/` 는 근거 없는 상수다 |

### 🔴 이전 보고의 정정

「`1830` 은 필수(Y)인데 가이드라인은 조건부라 모순」이라고 보고했다. **틀렸다** —
전 행이 `Y` 라서 `Y` 에 판별력이 없다. 모순이 아니라 **문서가 원래 그런 문서**다.

### 🔴 KC `0200` — 품목 23 만 「대상 아님」이 «빠져» 있다

```
품목 06·07·08·09·10·11·12·13·14·15·25 의 0200
   「인증 대상이 아닌 경우에는 "대상 아님"을 선택해 주세요.」        ← 있다

품목 23 (어린이제품) 의 0200                                      ← «없다»
   「｢어린이제품 안전 특별법｣에 따른 안전인증ㆍ안전확인ㆍ공급자적합성확인
     대상어린이제품에 한해 기재해주세요.」
   「어린이제품 및 방송통신기자재는 개정 전안법특례대상이 아니므로
     구매대행/병행수입을 «선택할» 수 없습니다.」
```

문장이 **`0200` 의 「선택」에 한정**된다 — 「구매대행으로 판매할 수 없다」가 아니다.
그리고 「구매대행」은 **문서 전체에서 이 한 번만** 나온다.

## 2. 🟢 `0070` × `0200` 은 모순이 아니었다 — 소관 법이 다르다

문의 2로 물으려던 것이 공개 법령으로 풀린다. **법 해석은 하지 않고 사실만 적는다.**

```
구매대행 특례의 근거    전기용품및생활용품안전관리법(전안법) 제10조②·제19조② 단서
                        → 시행규칙 제56조 → 【별표 13】 구매대행의 특례 제품
별표 13 의 구성         ① 안전인증대상 전기용품 ② 안전인증대상 생활용품
                           (그 중 「라. 섬유 = 대상 없음」) ③ 안전확인대상 전기용품
🔴 별표 13 에 «어린이제품도 방송통신기자재도 없다» — 둘은 전안법 소관이 아니다
```

→ 롯데ON 이 `0200` 에서 「개정 전안법특례대상이 아니므로」라고 쓴 것과 **부합하는 공적
사실**이다. 반면 `0070` 의 「병행수입의 경우 '병행수입'으로 기재」는 **표기 지시**이고
특례 여부와 층이 다르다. 🔴 **「구매대행/병행수입 특례」를 한 묶음 용어로 쓰는 근거는
법령 텍스트에서 찾지 못했다.**

### 그리고 아동 의류는 «한 유형이 아니다»

```
유아용 섬유제품   안전확인대상어린이제품        → CHL_CFM  축
아동용 섬유제품   공급자적합성확인대상어린이제품 → CHL_SUPS 축
```
🔴 현재 화면은 `selectedCategory?.safetyTypeCodes[0]` — **카테고리가 여러 유형을
플래그해도 첫 번째만** 쓴다. 유아용/아동용 경계에서 틀릴 수 있다(이번 스프린트 범위
아님 · `COMMON 후보` 아님 · **기록**).

## 3. 🟢 안전인증 코드 — 공개 JSON 백엔드에 표로 있다

```
GET https://soapi.lotteon.com/soapi/v1/openapi/o/apiguide/getApiGuideDetailInfo
    ?apiNo=87&apiMjrVerCd=V1&apiMnrVerNm=1.0&mdulDvsCd=SL     → 200 · 무인증
```

`sftyAthnTypCd` **[공통코드 : SFTY_ATHN_TYP_CD] · 20개**. 어린이제품 셋:

```
CHL_ATHN   [어린이제품] 안전인증           (수입대행코드 필수 «아님»)
CHL_CFM    [어린이제품] 안전확인           (같음)
CHL_SUPS   [어린이제품] 공급자적합성확인    (같음)
```

🟢 「수입대행코드 필수」 비고가 붙은 것은 **정확히 15개**이고, 우리
`SAFETY_TYPES_REQUIRING_IMPORT_PROXY`(`validate-payload.ts:53`)와 **완전히 일치**한다.
그 주석의 「문서에서 그대로 옮긴 것이고 추론이 아니다」는 🟢 **사실이었다.**

```
impPrxCd  [공통코드 : IMP_PRX_CD]   PUR_PRX 구매대행 · PRL_IMP 병행수입 · NONE 해당없음
impDvsCd  [공통코드 : IMP_DVS_CD]   DRC_IMP 공식수입 · PRL_IMP 병행수입 · NONE 해당없음
```

🔴 **`IMP_DVS_CD` ≠ `IMP_PRX_CD`** — 첫 항목이 `DRC_IMP 공식수입` 이고 `PUR_PRX` 가
아니다. 치환 금지.

### 🔴 여기서 나온 «실제 결함» 하나 (이번 스프린트 범위 밖 · 기록)

```
impCoNm   수입사명   Common product.importer 에서 «자동 전송» 된다
impDvsCd  수입구분   「수입사명이 있는 경우 입력한다」인데 UI·폼에 칸이 «없어»
                     항상 null 로 나간다
```
→ 수입사명이 있으면 조건부 필수인 값을 **구조적으로 못 보내는 상태**다. `COMMON 후보`
아님 · **CLEANUP CANDIDATE** 로 기록한다.

### 문서끼리 어긋나는 것 (Known Unknown)

```
ELC_AHTN(87) vs ELC_ATHN(90·94)   오타가 어느 쪽인지 문서로 결정 불가
                                   아동의류에는 쓰이지 않아 현재를 막지 않는다
apiNo 94 는 20개 중 17개만 게시     향후 LotteON UPDATE(GET baseline) round-trip 위험
sftyAthnNo 형식                     🔴 공개 자료에 «존재하지 않는다» — 우리가 형식
                                   검증을 만들면 근거 없는 정책이 된다
150개 공통코드 그룹 목록            88/89 문서가 게시하지 않는다. 그룹 이름은 «개별 API
                                   문서의 [공통코드 : XXX] 표기» 로만 얻는다
                                   🔴 `PD_ARTL_CD` 는 여전히 어디에도 없다(정정 유효)
```

## 4. 구현 — `0220` · `1830` 을 셀러 확인 경로에 붙였다

### 바뀐 판정

```
이전   0220 · 1830 → BLOCKED   근거: 「우리가 만들 수 없다」
정정   0220 · 1830 → NEEDS_INPUT  「우리가 채울 수 없다」≠「등록할 수 없다」
```

셀러는 자기 상품의 출시년월을 알고, 크기·체중 제한이 있는지도 안다. 공식 PDF 에
우리가 값을 정할 근거가 «없다» — 그래서 **셀러가 넣는다.**

### 바꾼 것 (5파일)

| 파일 | 변경 |
|---|---|
| `packages/listing/src/lotteon/notice-resolve.ts` | `sellerArticleValues` 추가 · `LOTTEON_SELLER_FILLABLE_ARTICLE_CODES` **화이트리스트** · `0220`/`1830` → `NEEDS_INPUT` |
| `packages/shared/src/product-types.ts` | `LotteOnChannelInfo.notice.articleValues?` (jsonb · **migration 0**) |
| `apps/admin/.../lotteon-channel-form.ts` | 폼 칸 + `noticeArticles` 로 합류 + 왕복 보존 |
| `apps/admin/.../lotteon/_lib/build-context.ts` | 같은 입력을 resolver 에도 준다 |
| `apps/admin/.../LotteOnRegistrationPanel.tsx` | **항목명** 입력칸(코드 비노출) |

### 🔴 왜 화이트리스트인가

전 항목을 열면 셀러가 `0200`(KC)에 아무 문자열이나 넣는다. 「KC 값을 지어내지
않는다」(「12313ㄹㅇ」 사건)가 **셀러 입력으로 우회되면 안 된다.** 가드가 이것을
직접 센다 — `0200`/`0080`/`0060` 에 값을 넣어도 payload 에 나가지 않는지 확인한다.

### 🔴 왜 «두 곳» 에 같은 값을 주는가

`build-context` 의 `mergeNoticeArticles` 는 이미 폼을 우선해 payload 에 얹는다.
그런데 resolver 가 그 값을 못 보면 **payload 에는 값이 가는데 화면은 「입력 필요」**
로 남는다. 그 갈라짐이 STEP3-FIX 의 병이다. 그래서 같은 입력을 resolver 에도 준다.
가드가 「상태와 payload 가 같이 움직이는지」를 센다.

### 지키고 있는 금지

`pdArtlCd` 직접 입력 ❌(항목명으로 묻는다) · 날짜 추정 ❌ · `N/A`/「해당없음」 자동
생성 ❌ · Master 새 필드 ❌ · Common 새 필드 ❌ · migration ❌ · KC 셀러 우회 ❌
