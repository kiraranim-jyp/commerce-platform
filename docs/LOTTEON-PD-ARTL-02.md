응답에 `probeOnly: true` 를 실어 둡니다 — 나중에 이걸 «기능» 으로 오인해 화면이
붙는 일을 막기 위해서입니다.

## 3. STEP 4 — 204 증거 (코드 변경 없음, 사실만)

**공식 명칭 `브랜드 조회`.** 엔드포인트 `onpick-api.lotteon.com/cheetah/econCheetah.ecn?job=cheetahBrnd`

### 요청 파라미터

| 파라미터 | 필수 | 의미 |
|---|---|---|
| `job` | **필수** | `cheetahBrnd` |
| `mf_1` | 선택 | 「브랜드 이름(brnd_nm): **중간 일치** 제공」 |
| `filter_1` | 선택 | 브랜드 ID(`brnd_id`) 정확 조회 |
| `between_start_1` / `between_end_1` | 선택 | 수정일 범위 |
| `skip` / `limit` | 선택 | 기본 0 / 100 |
| `sort` / `direction` | 선택 | 수정일 또는 브랜드 ID |

### 응답 필드

```
brnd_id           브랜드ID (12)          ← 식별자
brnd_nm           브랜드대표명 (255)
brnd_nm_kr        브랜드한글명 (255)
brnd_nm_en        브랜드영문명 (255)
brnd_nm_etc1/2    브랜드기타명 1·2 (255)
synonym_keyword   브랜드동의어 (255)
typo_keyword      브랜드오타어목록 (255)
brnd_sct_cd       브랜드유형명코드 (30)
brnd_nm_main_cd   브랜드대표명구분코드 (30)
use_yn            사용여부 (1)
brnd_desc / brnd_logo_img_url1 / mod_date
```

### 🔴 그런데 «같다» 고 말할 수 없는 것이 하나 있습니다

```
204 응답 식별자     brnd_id
우리 payload 필드   brdNo
```

**이 둘이 같은 값이라는 근거는 아직 없습니다.** 이름이 다릅니다. 확인 전에는
연결하지 않습니다 — 이번 스프린트가 바로 「이름을 추측해서 조회했다」로 무너진
건이기 때문입니다.

### 동명 브랜드를 가를 수 있는가

`use_yn`(사용여부)과 `brnd_nm_main_cd`(대표명구분코드) 둘뿐입니다.
**「대표 브랜드」를 직접 말해 주는 필드는 없습니다.** 동의어·오타어까지 주므로
검색은 강하지만, **여러 건이 나왔을 때 우리가 하나를 고를 공식 기준은 없습니다.**

→ 따라서 **자동 매핑은 지금 구현하지 않습니다.** CPO 지시 그대로입니다.
기존 상태(셀러에게 `brdNo` 를 묻지 않음 · 임의 매핑 없음)를 유지합니다.

### 기존 문서 정정

```
docs/COMMON-COMMERCE-AUTO-MAPPING-P0.md:47  「204 속성모듈 — 부르는 코드가 없다」
docs/COMMON-COMMERCE-AUTO-MAPPING-P0.md:71  「204 없이는 brdNo ↔ 브랜드명 매핑 근거가 전무」
```

**둘 다 틀렸습니다.** 204 는 속성이 아니라 **브랜드 조회**이고(속성은 203),
「매핑 근거 전무」도 사실이 아니었습니다 — 근거는 공식 문서에 있었습니다.
다만 근거가 있다는 것과 **자동으로 고를 수 있다**는 것은 다릅니다(위 문단).

**본문**

> `pdArtlCd`(상품항목코드)와 `pdArtlCnts`(상품항목내용)로 구성되는 것으로 확인했습니다.
>
> 문서 예시에는 `pdArtlCd: "0020"`(색상), `"0060"`(제조국)이 제시돼 있으나,
> **품목(`pdItmsCd`)별로 사용 가능한 `pdArtlCd` 전체 목록**은 확인하지 못했습니다.
>
> 다음 네 가지를 확인 부탁드립니다.
>
> 1. `pdArtlCd` 의 코드표(품목별 항목 목록)를 제공하는 **공식 문서 또는 API** 가 있습니까?
> 2. 공통코드로 제공된다면, **공통코드 그룹조회(API 88)에서 확인해야 하는 정확한
>    `grpCd`** 는 무엇입니까?
> 3. 공통코드 상세조회(API 89)로 조회 가능하다면 그 `grpCd` 도 함께 알려주실 수 있습니까?
> 4. 위 경로가 없다면, 상품등록 시 `pdItmsArtlLst` 를 **어떤 공식 기준**으로
>    구성해야 하는지 안내 부탁드립니다.
>
> 참고로, 이 값이 비어 있는 상태로 상품등록을 시도했을 때
> `9999 / 상품품목항목코드 필수값이 누락입니다` 로 응답받았습니다.
>
> 코드 체계를 임의로 추정해 등록할 경우 고시 정보가 잘못 노출될 수 있어,
> 공식 기준을 확인한 뒤 진행하고자 합니다. 감사합니다.

## 5. 🔴 CPO 결정 요청 — 88 응답을 «어떻게» 받을 것인가

보안 조건과 제 접근 권한이 충돌합니다. 제가 임의로 고르지 않습니다.

| 안 | 내용 | 대가 |
|---|---|---|
| **①** | 로그인된 브라우저에서 `/api/lotteon/code-groups` 를 **한 번** 연다 | 사람이 1회 클릭. 제품 테스트가 아니라 URL 열기 |
| **②** | 조사 기간 동안만 인증 가드를 뺀다 | 🔴 **권하지 않습니다.** 미인증 상태로 우리 API Key 를 쓰는 외부 호출 경로가 열립니다 |
| **③** | 서버 측 1회용 토큰 헤더를 추가 | 새 시크릿 관리가 생깁니다. 조사 한 번에는 과합니다 |

🔴 **제 권고는 ①입니다.** 그리고 ①을 고르시더라도 **제가 먼저 요청하지
않았습니다** — 결정은 CPO 몫입니다.

참고로 `common-codes` 와 `delivery-settings` 는 **지금도 앱 레벨 인증이 없습니다.**
그래서 그 둘은 제가 부를 수 있었고, 88 은 부를 수 없습니다. 이 비대칭 자체가
별도 보안 항목으로 남아 있습니다(이번 범위 아님).
