## 0. 🔴 가장 먼저 — P0-5 의 원인이 나왔다. 「입력 필요」가 **두 종류**다

CEO 께서 「준비됐다는데 왜 등록을 못 하지」로 보신 것의 구조다.

| | 누가 붙이나 | 등록을 막나 | 어디에 |
|---|---|---|---|
| **placeholder** 「입력 필요 — 상품정보에서 채워주세요」 | 🔴 **화면** (`LotteOnRegistrationPanel:2372`) | ❌ **막지 않는다** | ① 기본 상품정보의 빈 칸 |
| **알약** 「입력 필요」 | **서버 검증** (`commerce-registry:152` ← `MissingKind`) | ✅ **막는다** | 우측 등록 준비 상태 |

🔴 **같은 글자인데 결과가 다르다.** 사용연령·품명·모델명은 `summarizeCommonProduct`
에서 `missing: false` 로 설정돼 있고(주석: *「이 여섯 개가 롯데ON 등록을 막는지는
서버 검증이 정한다 — 화면이 여기서 새로 판정하면 등록 게이트가 두 벌이 된다」*),
그 판단은 **옳다.** 문제는 **두 상태가 같은 문구를 쓰는 것**이다.

### 🔴 그리고 상단 배너는 «다른 화면» 이다

```
settings/page.tsx:392   「✓ 상품 등록에 필요한 설정이 모두 준비되어 있습니다.」
  ← 설정 화면의 배너다. 재는 것은 «판매자 설정» 이다.
상품 화면 우측          「등록 준비 상태」
  ← 재는 것은 «이 상품의 필수 필드» 다.
```

**두 문장의 주어가 다르다.** 그런데 둘 다 「준비」라는 말을 쓴다. CPO 께서
지적하신 *「판매자 설정 준비 ≠ 상품 등록 준비」* 가 정확히 이것이다.

🔴 그 배너에 이미 같은 계열의 사고 기록이 있다 —
*「S-15(CEO 실화면) — Commerce 이름을 문구에 박지 않는다. … 지금도 롯데ON 이
빠져 있어 이 문장은 «사실이 아니었다»」*. 같은 자리에서 두 번째다.

**분류: ⑤(문구·축 분리 필요) — 값 자동화 문제가 아니다.**

## 1. P0-1 기본 상품정보 — 🔴 「매핑 없음」이 아니라 **「Master 에 값이 없다」**

전수 결과: ① 섹션의 **14행 전부 읽기 전용**이고 **롯데ON 탭에 편집 경로가 0개**다.
값은 모두 `CanonicalProduct` 에서 직결된다.

| 화면 | Common 출처 | payload | 분류 |
|---|---|---|---|
| 상품명 | `titleKo`→`resolveLotteOnProductName` | `spdNm` | ① 자동 |
| 브랜드 | `brand` | (텍스트 표시 · 코드는 ⑪) | ① 자동 |
| 상품코드(SKU) | `sku` | `eitmNo` | ① 자동 |
| 소재 · 색상 | `material` · `color` | 고시 내용 | ① 자동 |
| 제조사 | `manufacturer` + 브랜드프로필 | `mfcrNm` | ① 자동 |
| 옵션 · 재고 · 가격 · 이미지 · 상세 | 각 Common 필드 | 자동 | ① 자동 |
| **사용연령** | `recommendedAge` | 고시 내용 | 🔴 **③** |
| **품명** | `itemName` | 고시 내용 | 🔴 **③** |
| **모델명** | `modelName` | `mdlNo` | 🔴 **③** |

🔴 **셋은 「LotteON 이 다시 묻는」 것이 아니다.** 필드는 이미 연결돼 있고
**`CanonicalProduct` 의 그 값이 «비어 있다».** 화면은 placeholder 를 보여줄 뿐이고
등록을 막지도 않는다.

→ **문제의 자리는 롯데ON 어댑터가 아니라 «원상품 추출(크롤러)» 이다.**
이것이 이번 감사가 뒤집은 것이다. 롯데ON 쪽을 고쳐도 해결되지 않는다.

🔴 **자동값을 만들지 않았다** — 「모델명 ← SKU」 같은 추정을 넣지 않았다.
`modelName` 과 `sku` 는 다른 축이다(모델명은 제조사가 붙인 이름, SKU 는 판매 단위 식별자).

## 2. P0-2 상품정보고시 — 🔴 자동화를 막는 것이 **둘**이다

### 지금 화면

```

고시 내용 참고           11개 값을 «참고 목록» 으로만 보여준다
```

`collectLotteOnNoticeSourceValues` 가 모으는 11개 — 소재 · 색상 · 치수 · 제조사 ·
제조국 · 취급주의 · 권장연령 · 품명 · 모델명 · 수입사 · KC 인증유형.

🔴 **그 값들은 입력칸에 «주입되지 않는다».** 화면 문구가 「다시 입력하지 마세요」인데
실제로는 셀러가 옮겨 적어야 한다.

### 막는 것 둘 — 구분해서 적는다

```
(가) 채널이 주지 않는 것   품목별 «항목코드» 목록 API 가 없다   → 확정(P1-D)
                           89 PD_ARTL_CD rowCount 0 · 205 pd_itms_list empty
(나) 우리가 안 한 것       11개 내용값을 입력칸에 채워 주지 않는다
```

🔴 **그런데 (나)만 해도 등록은 안 된다** — `pdArtlCd`(왼쪽 코드)가 없으면 검증기가
막는다(`noticeArticles.every(a => a.pdArtlCd && a.pdArtlCnts.trim())`).
**내용만 채워 주는 것은 반쪽이다.**

### SmartStore·Coupang 이 되는 이유 — 재료가 다르다

```
Naver     카테고리 API 가 productInfoProvidedNotice 의 «필드 구조» 를 준다
Coupang   카테고리 API 가 noticeCategories[].noticeCategoryDetailNames[] 를 준다
LotteON   카테고리 API 는 «품목코드만» 준다 (noticeItemCodes)
```

**분류: ⑥(정보 부족으로 판단 불가) 유지.**
🔴 등록 성공 사례가 0건이라 94 로 실물 항목코드를 볼 수도 없다.
