## 0. 🔴 먼저 보고할 것 — 승인 ①과 보류 ⑤가 서로 걸립니다

CPO 판정은 이렇습니다.

```
①  0080 품질보증기준 / 0090 A/S  →  다음 구현 스프린트 «승인»
⑤  364행 고시 schema             →  현행성 확인 전 «코드화 금지»
```

그런데 **`0080`·`0090` 이라는 숫자 자체가 그 표의 행입니다.**

```ts
{ pdArtlCd: "0080", pdArtlCnts: <품질보증기준> }
              ↑
      이 코드는 오직 그 표에서만 온다
```

즉 ①을 구현하려면 **표의 일부를 코드에 들여야 합니다.** 제가 임의로
「두 줄뿐이니 괜찮다」고 넘기지 않겠습니다 — 판단을 §4 에 올립니다.

---

## 1. 표의 구조 — 추가로 확인한 사실

추출한 364행을 분석했습니다.

```
총 364행 · 고유 항목코드 164개 · 40품목이 이 164개를 «공유» 한다
```

같은 항목코드가 품목을 건너 같은 뜻으로 쓰입니다 —
`0020` 색상 · `0060` 제조국 · `0070` 제조자·수입자 · `0080` 품질보증기준 ·
`0090` A/S 책임자와 전화번호. 우리가 쓸 코드 10개는 **전부 일관**했습니다.

🔴 **다만 완전히 균일하지는 않습니다.** 표기가 갈리는 코드가 있습니다 —

```
0490   「사용상 주의사항」  vs  「사용할 때의 주의사항」
0620   「원료명 및 함량」    vs  「원재료명 및 함량」
1210   「유효기간, 이용조건」 vs  「이용조건, 이용기간」
```

→ 따라서 **「항목코드 = 전역 사전」으로 다루면 안 됩니다.**
**품목별로 읽는 구조**가 맞습니다(`pdItmsCd` → 그 품목의 행들).
이건 API 87 문서가 `pdArtlCd` 에 공통코드 참조를 «달지 않은» 것과도 맞습니다.

## 2. ② Common 데이터 연결 설계 (설계만, 구현 0)

### 2-A. 지금 값이 흐르는 길 — 실측

```
seller_settings (DB, migration 059)
   manufacturer · as_contact_number · quality_guarantee
   · kc_exemption_text · default_country_of_origin
        │
        └─ apps/admin/src/lib/seller-settings.ts
              loadSellerSettings() → { manufacturer, asContactNumber,
                                       qualityGuarantee, … }
                    │
       ┌────────────┴─────────────┐
       ▼                          ▼
   쿠팡 🟢 «이미 연결»           롯데ON 🔴 «연결 없음»
   payload-preview/route.ts:114
   register/route.ts:506
```

### 2-B. 들어갈 자리는 «이미 있는 자리» 입니다

롯데ON 고시는 여기서 만들어집니다 —

```ts
// apps/admin/src/app/api/lotteon/_lib/build-context.ts:205
noticeArticles: (form.noticeArticles ?? [])
  .filter((a) => a.pdArtlCd?.trim() && a.pdArtlCnts?.trim()),
```

**폼에서 온 것만** 봅니다. 그리고 그 폼 칸은 `readOnly` 에 값이 없습니다.

🔴 **그런데 바로 이 파일에 이미 «사다리» 가 있습니다** — 배송 여섯 값이
`fixed(form.X, sellerSettings.X)` 로 폼 → 설정 순서를 탑니다(`:225`).
STEP3-FIX 에서 화면까지 그 사다리에 맞춘 그 구조입니다.

**즉 새 패턴이 필요 없습니다. 같은 자리에 같은 모양으로 붙습니다.**

### 2-C. 제안 형태 (구현하지 않음)

```
noticeArticles =
      폼에 셀러가 확정한 항목        ← 먼저
    + 공통에서 채울 수 있는 항목      ← 폼에 없는 코드만

규칙
  · 코드는 «품목 schema» 에서만 온다 — 지어내지 않는다
  · 값이 없으면 «그 항목을 넣지 않는다» — 빈 문자열을 넣지 않는다
  · 폼 값이 있으면 공통이 덮지 않는다 (배송 사다리와 같은 순서)
  · 화면은 payload 와 «같은 사다리» 를 본다 (STEP3-FIX 에서 배운 것)
```

### 2-D. 🔴 그래서 무엇이 실제로 풀리는가 — 과장하지 않겠습니다

| 코드 | 공통 값 | 연결하면? |
|---|---|---|
| `0080` 품질보증기준 | `seller_settings.quality_guarantee` | 🟢 **채워진다** |
| `0090` A/S 책임자와 전화번호 | `as_contact_number` **만** 있음 | 🔴 **채워지지 않는다** |

고시가 「**책임자(업체명)와 전화번호 모두**」를 요구합니다. 우리에겐 번호뿐입니다.
**번호만 넣는 것은 「모두 입력」이 아닙니다.**

→ **`0090` 은 배선을 해도 완성되지 않습니다.** 업체명 결정(= CPO STOP 중)이
먼저입니다. `0080` 만 실제로 채워집니다.

그리고 13항목 중 하나가 채워져도 **등록은 여전히 막힙니다** — 검증기는 13항목
전부를 요구합니다. 🔴 **이 배선이 등록을 뚫는 작업이 아니라는 점**을 분명히
적어 둡니다.

**본문**

> 안녕하세요. 오픈API 로 상품등록(API 87)을 연동 중이며, 상품정보제공고시
> (`pdItmsInfo`) 작성과 관련해 문의드립니다.
>
> API 87 문서의 `pdItmsInfo` 설명란에 링크된 「23년 1월 상품정보제공고시
> 개정반영」 자료에서 품목별 항목코드(`pdArtlCd`) 표를 확인했습니다.
> 그 표를 기준으로 아래를 여쭙습니다.
>
> ---
>
> **A. 어린이제품 구매대행/병행수입 정책**
>
> 위 자료의 품목 `23`(어린이제품) 항목 `0200`(KC 인증정보) 작성 가이드라인에
> 다음 문구가 있습니다.
>
> > 「어린이제품 및 방송통신기자재는 개정 전안법 특례대상이 아니므로
> >  구매대행/병행수입을 선택할 수 없습니다.」
>
> 1. 위 문구가 **현재도 유효**합니까?
> 2. 품목코드 `23` **전체**에 적용됩니까, 아니면 일부 유형에만 적용됩니까?
> 3. **해외 구매대행 판매자**에게 적용되는 내용입니까?
> 4. **아동의류**는 품목 `01`(의류)과 품목 `23`(어린이제품) 중 어느 쪽으로
>    등록해야 합니까? 두 품목의 **구분 기준**을 알려주십시오.
> 5. 이 정책은 상품등록 API 의 **어떤 필드/선택값**으로 판정됩니까?
>    (수입대행코드 `impPrxCd` 인지, 안전인증유형인지)
> 6. **예외 또는 별도 등록 절차**가 있습니까?
>
> ---
>
> **B. 필수 고시값 작성기준**
>
> 7. `0210`(품명 및 모델명) — **모델명이 원천에 존재하지 않는 상품**은 어떻게
>    기재합니까?
> 8. `0220`(동일모델의 출시년월) — **형식**(예: `YYYY-MM`)과, 출시년월을
>    **확인할 수 없는 경우**의 처리 방법을 알려주십시오.
> 9. `0790`(사용연령 또는 권장사용연령) — 아동의류에서 **상품 옵션의 연령
>    표기**(예: `6-7 Years`)를 이 항목의 값으로 사용할 수 있습니까?
>    아니면 별도 기준이 있습니까?
> 10. `1830`(크기ㆍ체중의 한계) — 가이드라인이 「착용 또는 탑승용 어린이제품과
>     같이 크기ㆍ체중에 제한이 있는 품목」이라고 조건을 달고 있습니다.
>     **해당하지 않는 상품**은 어떤 값을 보내야 합니까?
>     (공란 허용 / 「해당없음」 / 그 밖의 표기)
> 11. `0090`(A/S 책임자와 전화번호) — 「업체명과 전화번호 모두」 기재하도록
>     안내돼 있습니다.
>     - 개인사업자 / 법인사업자의 경우 각각 **어떤 명칭**을 사용합니까?
>     - **판매자명과 A/S 업체명이 동일**한 경우에도 별도로 기재해야 합니까?
>     - 두 값을 **하나의 문자열**로 보내야 합니까, 별도 항목이 있습니까?
>
> ---
>
> **C. 자료 현행성**
>
> 12. 위 자료(「23년 1월 상품정보제공고시 개정반영」)가 **현재 유효한 작성
>     기준**입니까?
> 13. 이후 **개정판이나 별첨 자료**가 있습니까? 있다면 받을 수 있는 경로를
>     알려주십시오.
> 14. 품목별 항목코드(`pdArtlCd`)를 **API 로 조회**할 수 있는 방법이 있습니까?
>     (공통코드 그룹조회(API 88)에서 확인한 목록에는 해당 코드그룹이 없었습니다.)
>
> ---
>

> `9999 / 상품품목항목코드 필수값이 누락입니다` 로 응답받았습니다.
>
> 코드나 값을 임의로 추정해 등록할 경우 고시 정보가 잘못 노출될 수 있어,

## 4. CPO 판단 요청

### ① §0 의 충돌 — `0080` 배선과 364행 보류

세 가지 중 하나를 정해 주십시오.

| 안 | 내용 |
|---|---|
| **A** | **문의 답변(C-12/13)을 기다린 뒤** 표를 채택하고 그때 `0080` 을 배선한다 |
| **B** | **품목 23 의 13행만** 출처·판본을 붙여 상수로 들이고 `0080` 만 배선한다 |
| **C** | 코드 문자열 없이 배선할 방법을 찾는다 → 🔴 **없습니다.** `pdArtlCd` 가 필수라 코드 없이는 항목을 만들 수 없습니다 |

🔴 **제 권고는 A 입니다.** `0080` 하나를 배선해도 **등록은 뚫리지 않고**
(13항목 전부 필요), 현행성이 확인되면 13행을 한 번에 들이는 편이
「두 줄 먼저, 나머지는 나중」보다 깨끗합니다. 급할 이유가 없습니다.

### ② `0090` 은 배선 대상에서 빼야 합니다

번호만으로는 고시 요구(「업체명과 전화번호 모두」)를 만족하지 못합니다.
**배선해도 값이 완성되지 않으므로**, 업체명 결정 전까지는 `0080` 과 묶지
않는 것이 맞다고 봅니다. 문의 B-11 이 그 답을 가져옵니다.
