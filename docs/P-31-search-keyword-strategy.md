# P-31 — Naver DataLab 검색어 전략 설계안 (구현 아님, 정책 제안)

- 작성: CTO
- 작성일: 2026-09-03
- 상태: **설계만 완료. 현행 브랜드 검색 구조는 변경하지 않았다**(CPO 지시)

## 0. 현행 구조

```
상품 → product.brand.value → DataLab 검색어 "Bobo Choses"
캐시: market_signal_cache (signal_type=SEARCH_INTEREST, cache_key=정규화 브랜드명)
TTL: OK 7일 / NO_DATA 1일 / AUTH·REQUEST 6시간 / TRANSIENT 30분 (P-30)
```

즉 **브랜드 단위 캐시 + 브랜드 단위 검색어**다.

## 1. 호출량 산정 (무료 한도 50,000회/월)

브랜드 단위 캐시는 상품 수와 무관하게 **브랜드 수 × (30일 ÷ TTL 7일)** 만큼만 호출된다.

| 캐시 단위 | 대상 수 가정 | 월 호출량 | 한도 대비 |
|---|---|---|---|
| 브랜드 (현행) | 200 브랜드 | 약 860회 | **1.7%** |
| 브랜드 | 1,000 브랜드 | 약 4,300회 | 8.6% |
| 상품 | 5,000 상품 | 약 21,500회 | 43% |
| 상품 | 12,000 상품 | 약 51,600회 | **초과** |

→ 브랜드 캐시는 한도에 여유가 크고, **상품 단위 캐시는 상품 수가 늘면 한도를 위협**한다.

## 2. 검색어 후보 비교

| 후보 | 정확도 | 캐시 효율 | 위험 |
|---|---|---|---|
| **A. 브랜드** (현행) | 낮음 — 브랜드 인지도는 알지만 개별 상품 수요는 모름. 브랜드 상품 전체가 같은 값을 공유 | 최상 (브랜드당 1행) | 니치 해외 브랜드는 `NO_DATA` 가능성 높음 |
| **B. 상품명** | 이론상 최고 | 최악 (상품당 1행) | 해외 상품명(`Curious Turnip`)은 국내 검색량이 사실상 0 → 대부분 `NO_DATA`. **정확도가 오히려 하락** |
| **C. 브랜드 + 상품명** (한 문자열) | 최악 | 상품 단위 | 긴 복합어는 국내 검색이 거의 없음 → `NO_DATA` 양산 |
| **D. 브랜드 + 핵심 상품 키워드** | 중간~높음 | 상품 단위 | 키워드 추출 로직(카테고리/소재/유형) 필요. `보보쇼즈 원피스` 같은 형태 |

**핵심 관찰**: B/C는 직관과 반대로 정확도를 떨어뜨린다. 해외 상품 고유명은 국내 검색 데이터가 없어 "관심 낮음"이 아니라 "데이터 없음"이 되고, 이는 신호로서 가치가 0이다.

## 3. 권장안 — 호출을 늘리지 않고 정확도를 올리는 방법

### 3-1. 핵심: DataLab은 **1회 호출에 키워드 그룹을 최대 5개** 실을 수 있다

현재는 그룹 1개만 쓰고 있다:

```json
"keywordGroups": [{ "groupName": "Bobo Choses", "keywords": ["Bobo Choses"] }]
```

여기에 그룹을 추가해도 **API 호출 수는 그대로 1회**다:

```json
"keywordGroups": [
  { "groupName": "brand",    "keywords": ["Bobo Choses", "보보쇼즈"] },
  { "groupName": "category", "keywords": ["보보쇼즈 원피스"] }
]
```

→ **후보 A와 D를 동시에, 추가 호출 없이** 얻을 수 있다. 이것이 "호출량을 늘리지 않고 정확도를 높이는" 유일한 경로다.

### 3-2. 부수 효과: 영문/한글 표기 동시 조회

한 그룹의 `keywords` 배열에 최대 20개까지 넣을 수 있고, **같은 그룹 내 키워드는 합산**된다. `["Bobo Choses", "보보쇼즈"]`처럼 표기 변형을 함께 넣으면 `NO_DATA` 비율이 떨어진다 — 역시 호출 수 증가 없음.

현재 니치 브랜드에서 `NO_DATA`가 나온다면 **영문 표기만 조회하고 있는 것이 원인일 가능성이 높다**(국내 검색은 한글 표기가 압도적).

### 3-3. ⚠️ 반드시 짚어야 할 의미 변화

한 요청 안의 모든 그룹은 **최댓값 하나를 100으로 공유**해 정규화된다. 그룹을 늘리면 기존 단일 그룹의 `ratio` 의미가 달라진다:

- 현재: "이 브랜드의 최근 3개월 중 최고점 대비 최근값"
- 변경 후: "요청 내 모든 그룹의 최고점 대비 최근값"

따라서 그룹 추가는 **`searchInterestLevel()` 임계값(50/10)의 재보정을 동반해야 한다.** 이 재보정 없이 그룹만 늘리면 지금보다 낮은 값이 나와 "관심 하락"으로 오독된다. 이번 스프린트에서 구현하지 않은 이유이기도 하다.

### 3-4. 캐시 설계 (권장안 채택 시)

```
cache_key: 브랜드 정규화 키 유지  (상품 단위로 내리지 않는다)
value_json: { brandRatio, categoryRatio, status, keyword }
```

카테고리 키워드를 `브랜드 + 카테고리`로 만들면 같은 브랜드·같은 카테고리 상품이 캐시를 공유한다. 캐시 키를 `brand::category`로 두면 행 수는 **브랜드 수 × 카테고리 수**로, 상품 수와 무관하게 억제된다.

| 방식 | 월 호출량(200 브랜드 기준) | 한도 대비 |
|---|---|---|
| 현행 브랜드 단독 | 약 860회 | 1.7% |
| 권장안(브랜드+카테고리, 1회 호출에 2그룹) | 약 860회 | **1.7% (동일)** |
| 캐시 키를 brand::category로 분리 시 (카테고리 평균 4개) | 약 3,440회 | 6.9% |

## 4. 권장 순서

1. **선행**: CEO의 1회 실호출로 `ratio: null` 원인 확정 (여전히 미해결)
2. 정상 확인 후 → `keywords`에 **한글 표기 추가**(그룹 1개 유지, 임계값 재보정 불필요, 호출 증가 없음) — 가장 싸고 안전한 정확도 개선
3. 그 다음 → 그룹 2개(브랜드/카테고리)로 확장 + **임계값 재보정 동반**
4. 상품명 단독(B)·브랜드+상품명(C)은 **채택 비권장**

## 5. 검증되지 않은 전제 ⚠️

- "키워드 그룹 최대 5개 / 그룹당 키워드 최대 20개"는 Naver DataLab 문서 기준이며, **이번 스프린트에서 실호출로 확인하지 않았다**(API 호출 0회 원칙). CEO의 1회 검증 때 그룹 2개를 함께 보내면 추가 호출 없이 확인 가능하다.
- 한글 브랜드 표기는 브랜드별 매핑 테이블이 필요하다. 자동 음역은 오탐 위험이 있어 권장하지 않는다.

# 부록. Market Intelligence Snapshot 보존 검토 (P-31 항목 7)

## 결론: **이번 스프린트에서는 DB 변경 불필요**

### 조사 결과

- 현재 Market Intelligence 결과(가격 CASE·마진·시장 신호·판정)를 저장하는 테이블은 **없다**. 매 요청마다 계산한다.
- 그러나 **계산 입력은 이미 전부 영속화되어 있다**: `price_observations`(국내/해외 관측가), `market_signal_cache`(검색 관심), 스냅샷의 상품 정보, `seller_profile`(원가 파라미터).
- 파생 로직은 전부 순수 함수다(`computePriceRecommendation`, `deriveMarketSignals`, `buildSellerDecision`).

### 판단 근거

입력이 보존되고 파생이 순수 함수이므로, **결과를 따로 저장하지 않아도 언제든 재현 가능**하다. 지금 스냅샷 테이블을 만들면:

- 같은 사실을 두 곳에 저장 → 정책이 바뀔 때마다(P-26·P-29·P-30·P-31처럼 실제로 자주 바뀌었다) 저장된 판정이 코드와 어긋나는 staleness가 생긴다.
- 소비자가 아직 없다 — 대시보드/상품 리스트/모니터링은 전부 미구현이다.

CPO 지시("단순히 미래 확장성을 이유로 불필요한 DB 구조를 만들지 않는다")에 정확히 해당한다.

### 스냅샷이 실제로 필요해지는 조건

아래 중 하나라도 현실이 되면 그때 도입한다:

1. **시계열이 필요할 때** — "이 상품의 판정이 지난달 대비 어떻게 변했나". 재현으로는 과거 시점 판정을 복원할 수 없다(당시 환율·원가·시장가가 사라짐).
2. **목록 화면에서 정렬/필터가 필요할 때** — 상품 1,000개의 판정을 매번 계산하면 응답이 무너진다.
3. **판정 변화 알림이 필요할 때** — 이전 판정이 저장돼 있어야 변화를 감지한다.

→ **차기 스프린트 제안**으로 이관한다.
